Building a SaaS with Cloudflare Workers + D1: A Complete Guide

April 20, 202610 min readBy the RevKlik Team

RevKlik is built entirely on Cloudflare: Workers for compute, D1 for the database, R2 for storage. Infrastructure cost? Under $10/month, even with hundreds of customers. This guide explains why this stack works so well for SaaS and how you can use it for your own product.

Why Cloudflare for SaaS?

Traditionally, SaaS founders choose AWS, GCP, or Vercel + PlanetScale/Supabase. These stacks work, but their cost grows with scale. Cloudflare offers a different model:

ComponentTraditionalCloudflare
Compute$20-100/month (EC2, Lambda)$0.30/million requests (Workers)
Database$15-50/month (RDS, PlanetScale)Free up to a limit, then ~$1/million writes (D1)
Storage$0.023/GB + egress (S3)$0.015/GB, no egress (R2)
CDN$20/month (CloudFront)Free and built-in
SSLFree (Let's Encrypt)Free and automatic

Total cost for an MVP with 10.000 active users: under $10/month. That includes the Workers Paid plan ($5/month). For context, a similar setup on AWS can reach $50-200/month.

The Architecture We Use at RevKlik

RevKlik has three main components:

1. Tracking Script (Client-Side)

A vanilla JS script embedded on customer sites. It is about 4 KB (gzip) and uses navigator.sendBeacon() to send events without blocking page rendering.

The script captures:

  • Pageviews (automatic)
  • UTM parameters from the URL
  • Session ID (stored in sessionStorage, not a cookie)
  • Custom events (called manually by the customer)

2. Ingestion Worker (Edge)

A Worker that receives events from the tracking script, validates them, and stores them in D1. It runs at the edge, which means requests are processed at the location closest to the visitor, not on a central server.

The same Worker also handles webhooks from Polar: it receives payment notifications and links them to the visitor's session for revenue attribution.

3. Dashboard Worker + Pages

The RevKlik dashboard itself is an app hosted on Cloudflare Pages, with API endpoints running on Workers. It queries D1 to show journey, funnel, and attribution data to customers.

Database Schema in D1

D1 uses SQLite, so a standard relational schema works fine. Here is the core of the schema we use:

-- Main table for events
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  tenant_id TEXT NOT NULL,
  session_id TEXT NOT NULL,
  visitor_id TEXT,
  timestamp INTEGER NOT NULL,
  event_type TEXT NOT NULL,
  path TEXT,
  utm_source TEXT,
  utm_medium TEXT,
  utm_campaign TEXT,
  revenue REAL,
  props TEXT, -- JSON string
  referrer TEXT
);

-- Indexes for fast queries
CREATE INDEX idx_events_tenant_session
  ON events(tenant_id, session_id, timestamp);

CREATE INDEX idx_events_tenant_type
  ON events(tenant_id, event_type, timestamp);

-- Sessions table for aggregation
CREATE TABLE sessions (
  id TEXT PRIMARY KEY,
  tenant_id TEXT NOT NULL,
  visitor_id TEXT,
  started_at INTEGER,
  utm_source TEXT,
  utm_medium TEXT,
  utm_campaign TEXT,
  referrer TEXT,
  event_count INTEGER DEFAULT 1,
  converted INTEGER DEFAULT 0
);

The right indexes are the key to D1 performance. With an index on (tenant_id, session_id, timestamp), a query to reconstruct a user journey finishes in milliseconds even with millions of events.

Multi-Tenancy: Two Approaches

For multi-tenant SaaS, there are two patterns that have proven to work:

Approach A: Shared Database with tenant_id

One D1 database for all customers. Every table has a tenant_id column and all queries include a WHERE tenant_id = ? filter.

Pros: Simple, one database to manage, easy cross-tenant analytics (for you as the platform owner).

Cons: Data isolation depends on query discipline. A single query without the tenant_id filter can leak data.

Approach B: Database Per Customer

Each customer gets their own D1 database. Cloudflare lets you create and bind databases programmatically.

Pros: Complete data isolation, no leak risk, per-tenant performance is isolated.

Cons: More complex to set up, and cross-tenant analytics needs manual aggregation.

For RevKlik, we use Approach A for its simplicity. The tenant_id filter is abstracted into middleware so it can't be forgotten.

The Most Important Queries

User Journey

Reconstruct a visitor's path from a single session:

SELECT path, event_type, timestamp, props
FROM events
WHERE tenant_id = ? AND session_id = ?
ORDER BY timestamp ASC;

To see the most common paths across all sessions:

SELECT path, COUNT(*) AS hits
FROM events
WHERE tenant_id = ?
  AND timestamp > ?
GROUP BY path
ORDER BY hits DESC
LIMIT 20;

Revenue Attribution

Total revenue per UTM source:

SELECT utm_source, utm_medium,
       SUM(revenue) AS total_revenue,
       COUNT(DISTINCT session_id) AS sessions
FROM events
WHERE tenant_id = ?
  AND revenue IS NOT NULL
  AND timestamp > ?
GROUP BY utm_source, utm_medium
ORDER BY total_revenue DESC;

Conversion Funnel

Count how many sessions pass through each funnel step:

WITH funnel AS (
  SELECT session_id,
    MAX(CASE WHEN path = '/pricing' THEN 1 ELSE 0 END) AS step1,
    MAX(CASE WHEN event_type = 'signup' THEN 1 ELSE 0 END) AS step2,
    MAX(CASE WHEN event_type = 'purchase' THEN 1 ELSE 0 END) AS step3
  FROM events
  WHERE tenant_id = ? AND timestamp > ?
  GROUP BY session_id
)
SELECT
  SUM(step1) AS saw_pricing,
  SUM(step2) AS signed_up,
  SUM(step3) AS purchased
FROM funnel;

Recommendations to Get Started

  1. Use Hono as your framework. Hono is light (~14KB), TypeScript-native, and works well on Cloudflare Workers. Don't use Express: it is too heavy for the edge.
  2. Start with a shared database. One D1 with tenant_id is enough for up to thousands of customers. Move to per-tenant databases only if truly needed.
  3. Use R2 for raw data. Store the full event JSON in R2 as a backup and for deeper analysis later.
  4. Add Cron Triggers for aggregation. Pre-compute frequently accessed numbers (daily visitors, revenue per source) every hour, instead of re-querying each time the dashboard is opened.
  5. Implement Polar webhooks in the same Worker. One Worker can handle both tracking events and payment webhooks, so no separate service is needed.

Limitations to Know About

  • Worker size: 10MB limit per Worker. For most SaaS this isn't a problem. If your code nears the limit, split it into several Workers.
  • CPU time per request: 50ms on the free plan, 30 seconds on the paid plan. A very heavy D1 query can approach this limit, so use pre-aggregation.
  • D1 database size: 10GB per database. For analytics with 1 million events/month, this is enough as long as you archive old data to R2.
  • No native WebSocket. For a real-time dashboard, use polling or upgrade to Durable Objects ($0.15/million requests).

Conclusion

Cloudflare Workers + D1 + R2 is a very efficient stack for SaaS. Low infrastructure cost lets you offer competitive prices while still keeping high margins. And because everything runs at the edge, performance for users in Indonesia is as good as for users in America.
