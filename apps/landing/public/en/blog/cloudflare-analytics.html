Why Edge-Native Analytics Is Faster and Cheaper

May 3, 20266 min readBy the RevKlik Team

Most analytics tools (Google Analytics, Mixpanel, Amplitude) run on centralized servers. Data from a visitor in Jakarta is sent to a data center in the United States, processed, then returned to your dashboard. That round trip takes hundreds of milliseconds.

Edge-native analytics changes this model completely. Data is processed on the server closest to the visitor. In RevKlik's case, that is the Cloudflare network with 300+ locations worldwide. The result: faster for visitors, cheaper for you, and better for privacy.

The cost difference is the most striking. In the traditional model, you pay for servers that have to handle all the traffic from around the world. In the edge model, the load is spread across hundreds of locations, each handling a small share of the traffic.

How Does Edge Analytics Work?

There are three main components in an edge analytics stack:

1. Edge Workers for Ingestion

When a visitor loads your page, the tracking script sends events to the nearest Worker, not to a central server. Cloudflare Workers handle these requests in milliseconds because they run on the same edge node as your site's CDN.

No extra DNS lookup. No TLS handshake with a distant server. Data enters the edge, gets processed, and gets stored.

2. D1 for Storage

Cloudflare D1 is a SQLite database that runs at the edge. For analytics, this fits well: every event is a single INSERT row. Dashboard queries (visitor counts, funnels, journeys) run directly at the edge.

D1's capacity is enough to handle millions of events per month at a very low cost: free up to a certain limit, then a few dollars per million operations after that.

3. R2 for Archive

Raw events can be archived to Cloudflare R2, an S3-compatible object storage with no egress fees. This means you can keep all your raw data without worrying about bandwidth costs spiking when you read it back.

Why Does Latency Matter for Analytics?

Tracking latency affects two things: your site's speed and the accuracy of your data.

Site speed: An analytics script that takes 200ms to send data will slow down page loading, especially on mobile connections. Each additional 100ms of delay lowers the conversion rate by about 1% (according to a Google study). An edge script that finishes in 5ms has no impact at all on the visitor's experience.

Data accuracy: Slow scripts tend to lose events because visitors close the page before the request finishes. navigator.sendBeacon() helps, but it is still better if the request completes within a few milliseconds. Edge analytics completes the request almost instantly, before the visitor has a chance to close the tab.

What About Local Data?

For businesses serving users in Indonesia, the PDP Law requires certain handling of user data. Edge analytics makes compliance easier because:

  • Data is processed on the nearest edge node, in or near Indonesia
  • No data is transferred to servers in other jurisdictions for processing
  • Data can be archived and deleted by location

This is not a full compliance solution. You still need a privacy policy and user consent. But edge-native makes implementation much simpler than a centralized server abroad.

When Is Edge Analytics Not the Right Fit?

An honest look at the limitations:

  • Complex queries across millions of events: D1 is very fast for per-tenant queries, but heavy analytical queries that scan tens of millions of rows are still better in a dedicated data warehouse.
  • Real-time machine learning: If you need an ML model to process every event, edge workers have CPU and memory limits.
  • Cross-source data joins: Combining analytics data with a CRM or an external data warehouse requires a separate ETL pipeline.

But for 95% of analytics needs (pageviews, event tracking, funnels, journeys, revenue attribution), edge-native is more than enough.
