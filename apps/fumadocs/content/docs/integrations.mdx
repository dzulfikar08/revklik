The **Integrations** view (top-bar tab) has five tabs: Webhooks, Payments,
Marketplace, Search, and Imports.

## Webhooks

API-key integrations for email and ads. Connect once and RevKlik pulls the
data in:

| Integration | What it syncs                        | Config                                               |
| ----------- | ------------------------------------ | ---------------------------------------------------- |
| Mailchimp   | Subscriber data and email engagement | API key + server prefix                              |
| ConvertKit  | Audience data                        | API key                                              |
| Kit         | Kit (formerly ConvertKit) v3 API     | API key                                              |
| Beehiiv     | Newsletter subscriber activity       | API key + publication ID                             |
| Meta Ads    | Ad performance and conversions       | Access token + pixel ID                              |
| Google Ads  | Campaign data                        | Client ID, client secret, refresh token, customer ID |

Each connection can be configured, tested, enabled, and disabled. The event
log records every webhook and test with direction, status, and time.

## Payments

Payment-gateway integrations are **webhook-driven**: copy the RevKlik webhook
URL shown on each card and paste it into the provider's webhook settings, then
store the signing key. Revenue lands in your revenue panels automatically.

| Provider      | Coverage                                           |
| ------------- | -------------------------------------------------- |
| Midtrans      | GoPay, QRIS, bank transfer, credit card, ShopeePay |
| Xendit        | OVO, DANA, ShopeePay, virtual accounts             |
| Stripe        | Cards, wallets, bank debits, subscriptions         |
| Lemon Squeezy | Digital products and SaaS billing                  |

### Server events API

For purchases a webhook cannot reach (App Store notifications, a backend of
your own), report them from your server:

```bash
curl -X POST https://<your-revklik-host>/api/v1/events/server \
  -H "Authorization: Bearer rv_..." \
  -H "Content-Type: application/json" \
  -d '{
    "site_id": "<site id>",
    "name": "purchase",
    "revenue": 9.99,
    "currency": "USD",
    "external_id": "<transaction id>",
    "source": "app_store",
    "props": { "product": "pro", "country": "ID", "environment": "Production" },
    "occurred_at": "2026-10-24T09:30:00Z"
  }'
```

Use a site token (`rv_`) with the `events:write` scope. `revenue` is in major
units; send a **negative** number for a refund, under its own key such as
`<transaction id>:refund`. The call is idempotent on `external_id`: a repeat
returns `"duplicate": true` and books nothing. Pass `visitor_id` (the
`_kp_vid` value from the browser) or `session_id` (`_kp_sid`) to attribute the
sale to that visitor's source and campaign. A `revenue` of `0` is stored as a
plain event, not a conversion.

### Rail, product and net revenue

Three optional fields feed the cross-product [portfolio view](#portfolio-revenue):

| Field | Meaning |
| --- | --- |
| `rail` | Payment rail, lowercase: `apple`, `google_play`, `polar`, `doku`, `pakasir`, `stripe`, `lemonsqueezy`, `midtrans`, `xendit`, `mayar`, `paywuz`, `manual`. Defaults from `source` (`app_store*` → `apple`, `google*` → `google_play`, `polar*` → `polar`, ...), else the source itself. |
| `product` | Product slug, up to 80 characters. Defaults to `props.product`, then `props.app`. |
| `net_revenue` | What you keep, in the same currency and sign as `revenue`, never larger in size. Send it only when the source knows the real proceeds (for example Apple's developer proceeds). |

Without `net_revenue`, RevKlik computes the net when the event is stored: the
fee is `|revenue| × percent + fixed amount` (the fixed amount is converted into
the event currency), and `net = max(0, |revenue| − fee)` with the sign of
`revenue`. A refund (`<id>:refund`) without `net_revenue` keeps the net/gross
ratio of the original sale. Each event records how its net was obtained
(`reported`, `rule` or `refund_ratio`). Nets are stored at ingest and never
recomputed when you edit a rule later. Replaying a sale with `net_revenue`
(for example re-running a Polar import) upgrades a stored `rule` estimate to
the `reported` figure.

Polar orders carry Polar's own fee (`platform_fee_amount`); the webhook and the
order import store `net_amount − platform_fee_amount` as the reported net, and
fall back to the 4% + 0.40 USD rule when Polar sends no fee. Revenue that the
buyer's browser already reported on the thank-you page (same site, source,
amount and currency, within an hour) is not booked a second time: the
confirmed order fills in that row with its order id, rail and net. The same
visitor firing the same conversion on the same page again within a minute is
stored but excluded as a duplicate.

### Test sales

A sale whose `source` or `rail` names a test (`tracking_smoketest`,
`test_checkout`, ...), or whose `props._test` is `true`, is stored with
`excluded_reason = "test"` and left out of every dashboard, API and MCP number,
like bot traffic. Double-booked sales are excluded the same way with
`excluded_reason = "duplicate"`.

Built-in fees (editable per rail on the Portfolio page, or `GET`/`PUT
/api/fee-rules` with a dashboard session): `apple` 15%, `google_play` 15%,
`polar` 4% + 0.40 USD, `stripe` 2.9% + 0.30 USD, `doku` 0.7%, `pakasir` 0.7%,
every other rail 0%. A stored sale with no net is never reported as net = gross:
the portfolio computes its net from your fee rule for its rail when you read
it, and reports how many rows were estimated that way (`estimated_rows`,
`net_source: "estimated"`). `bun scripts/backfill-revenue.ts` (in `apps/app`)
stores those nets, rails and exclusions on old rows.

### Portfolio revenue

```bash
curl "https://<your-revklik-host>/api/v1/portfolio/revenue?from=2026-10-01&to=2026-10-31&currency=IDR" \
  -H "Authorization: Bearer rvt_..."
```

Needs an account token (`rvt_`) with `analytics:read`; a site token only sees
its own site. It covers every site you own or have accepted a team seat on,
excludes bot traffic, and converts each sale at today's rates into `currency`
(default: your most common site currency). `from` and `to` are inclusive UTC
days (default: the last 30 days). The `data` object holds:

- `currency`, `from`, `to`
- `totals`: `gross`, `net`, `sales` (revenue > 0), `refunds` (revenue < 0),
  `refund_amount`, `estimated_rows` (rows whose net came from the fee rule at read time)
- `by_site`, `by_product`, `by_rail`, `daily`: `gross`, `net` and `sales` per group
  (`by_rail` also has `estimated_rows`; a row without a rail takes the rail its
  payment provider implies, e.g. `app_store_sales_report` → `apple`)
- `recent`: the 20 newest revenue events with `revenue`, `net_revenue`,
  `net_source`, `currency`, `converted_gross`, `converted_net` and `occurred_at`

The same data is available to AI agents as the `portfolio_revenue` MCP tool.

For Polar, put `revklik_visitor_id` and `revklik_session_id` in the checkout
metadata. RevKlik books `order.paid` and `order.refunded` once per order, using
the order's net amount (after discounts, before tax).

## Bot filtering

Traffic that is not a person is stored but flagged, and excluded from every
dashboard, API and MCP number. It is flagged when the browser reports
automation (`navigator.webdriver`), when Cloudflare Bot Management scores the
request as a bot, when it comes from a datacenter-only city, or when a session
behaves in ways a person cannot: several scroll depths in the same
millisecond within a few seconds of loading with no click, bursts of pageviews,
or more than 100 clicks. An hourly job re-judges recent sessions, so a rule
change reclassifies old data too.

Session duration counts each gap between two events up to 30 minutes, so a tab
left open overnight no longer inflates the average. Traffic sources are merged
by name: `bing`, `bing.com` and `www.bing.com` are one source, and only
pageviews from outside your own domain count as a source.

## Marketplace

Connect **Shopee** and **Tokopedia** with OAuth (or re-authorize when a grant
expires), then **Sync orders** to pull orders into RevKlik. **View orders**
lists recent orders with amount, status, and date.

## Search

**Google Search Console** imports search performance: authorize with Google,
then **Sync now** to pull clicks, impressions, CTR, and position per query.
The panel shows 30-day totals and a per-query table.

## Imports

Bring history in without waiting for it to accumulate:

- **Polar**: live orders stream in via a webhook URL; a one-time import can
  backfill existing orders, customers, and countries with a Polar
  organization ID and access token (`orders:read`,
  `subscriptions:read`, `organizations:read` scopes).
- **OneDollarStats**: import visitors, pages, countries, and sources with an
  API key and the site domain as registered there.

## Share and access

The **Share** tab bundles everything public:

- **Public dashboard**: a read-only link to your analytics; disable it any
  time.
- **Live widget**: an embeddable live-visitor bubble or badge:

  ```html
  <script
  	async
  	src="https://app.revklik.com/klikapa-live.js"
  	data-widget-token="YOUR_TOKEN"
  ></script>
  ```

- **API tokens**: account- or site-scoped tokens with granular scopes
  (`sites:read`, `analytics:read`, `analytics:export`, `tokens:read`,
  `tokens:write`). Limits depend on your plan; see [billing](/billing). The
  same tokens also work over [MCP](/mcp), so coding agents can read your
  analytics directly.

## Email reports

In **Settings → Email reports**, schedule a recurring summary to your account
email: **daily, weekly, or monthly**. Reports can be toggled on and off and
show when they were last sent.

## Team

In **Settings → Team**, invite teammates by email as **Admin**, **Editor**, or
**Viewer**. Invitees need an existing revklik account; owners can change roles
and remove members at any time.
